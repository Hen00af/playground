# Networkの基礎
## 目標
コンピュータネットワークは多重に抽象化された状態で存在している。
その抽象化の層を潜り込み、中身を理解していくことが本章の目標です。

### プロトコルの階層

ネットワークプロトコルは複数の層で抽象化されています。下層は上層の情報をペイロードとして保持しており、上層は下層に新たな機能を追加します。

これを現実世界で表すと、
イーサネットにIPが含まれ、IPにUDP/TCPが含まれ、UDP/TCPにアプリケーションプロトコルが含まれる、という層の流れになります。

さらに、この層を機能別に分割することも可能です。

```
｜ー小さな個別のメッセージの層（IP）
｜
｜
｜ー多重化レイヤー（ポート番号）
｜
｜
｜ー信憑性が高く順序づけられたバイトの層（TCP）
````


- 小さな個別のメッセージの層（IP）

巨大なファイルをダウンロードする時、ハードウェアは転送前にデータ全体を保存することはできず、より小さな単位（IP）でしか処理することができません。

そのため、最下層はパケットベースになっています。
パケットをアプリケーションで再構築する機能はTCPなどの上層で行われます。

- 多重化レイヤー

複数のアプリケーションが一台のパソコン上で同じネットワークを共有したい場合、その機能を実装するにはコンピュータがどのどのパケットがどのアプリケーションに属しているのかを知れる必要があります。

それを実現するために*マルチプレクサ*という機能を使用しています。

IPの次の層、つまりTCPかUDPは異なるアプリケーションを区別するために16ビットのポート番号を追加します。
各アプリケーションがIPを使用して送受信する際に未使用のローカルポート番号を取得しなければなりません。
コンピュータは４タプルを使用して情報の流れを識別します。

- マルチプレクサ

複数の信号を１つにまとめたり、逆に１つの信号を正しい入り口に仕分ける機能。
```
多重化（Multiplexing）: 送信時、各アプリから出たデータを一つのネットワーク回線に「相乗り」させること。

逆多重化（Demultiplexing）: 受信時、回線から届いたパケットを、ポート番号（4タプル）を見て「これはRedis宛」「これはブラウザ宛」と正しいアプリに配ること。
```
- 信頼性が高く順序づけられたバイトの層（TCP）

小さく大量に分割されたパケットが送受信された場合、送受信時に一部のパケットが破棄されたり順序が入れ替わったりすることがあります。

その対策として、IPパケットの上に信憑性が高く順序付けられたバイトのレイヤーを付け、欠けた場合の修復や順序の整理を自動で行うようにします。


- TCP/IPモデル

以上のことから、TCP/IPモデルが説明できます。
今までの話の流れから、ネットワークをするためのニーズは以下の東リだということがわかります。

1. IPパケット受信
2. 多重化レイヤーを用いたIPパケットのポート照合
3. TCPによる、IPパケットのcirializationによるオブジェクト化

### リクエスト・レスポンスプロトコル

Redis含め、ほとんどのRPCプロトコルはリクエスト/レスポンス プロトコルです。

TCPプロトコルが順序直したりしてくれる関係で、一強になってます。

しかし、ほとんどのアプリケーションはバイト列ではなく意味のあるオブジェクトを期待しているので、バイトストリームを解釈する機能をTCPにラップしています。
それをシグナリング（プロトコルによる意味付け）と言います。

### ソケットとは
ソケットは接続を参照するためのハンドルです。
ネットワーク用のAPIはソケットAPIと呼ばれ、それは異なるプラットフォーム間でも同様の仕組みになっている。

ハンドルとはAPI境界を超えるものを参照するために使用される不透明な整数です。
要するにFDのことです。
socket()メソッドはこのソケットのfdを割り当てて返します。

割り当てられたfdはもちろん、終了後に閉じなければなりません。
リソースは有限です。気をつけましょう。

### listningとaccept

アプリケーションが指定されたポートからのソケットを受け取る準備ができた際、OSに通知しなくてはなりません。（異なるプロセス間でソースのやり取りができるのはOSのみだからです。）

OSは、アプリケーションがそのポートを参照するためのソケットハンドルを返します。

リスニングソケットを作成するには、少なくとも3つのAPI呼び出しが必要です。

```
1, ソケットハンドルを取得しますsocket()。
2, リスニングIP:ポートを で設定しますbind()。
3, リスニングソケットを作成しますlisten()。
```

### クライアントから接続

クライアント側から2つのAPI呼び出しによって接続ソケットが作成されます。

ソケットハンドルを取得しますsocket()。
接続ソケットを作成しますconnect()。
擬似コード：
```
fd = socket()
connect(fd, address)
do_something_with(fd)
close(fd)
```
socket()は型指定のないソケットを作成します。

ソケットのタイプ（リスニングまたは接続）は、listen() またはconnect()呼び出し後に決定されます。

bind()と間の socket()はlisten()単にパラメータを設定するだけです。APIsetsockopt()は、後で使用される他のソケットパラメータを設定できます。

### 読み書き
send()TCPとUDPは異なる種類のサービスを提供しますが、メソッドや メソッドを含むソケットAPIは共通ですrecv()。

メッセージベースのソケット（UDP）の場合、各メソッドは send/recv単一のパケットに対応します。バイトストリームベースのソケット（TCP）の場合、各メソッドはsend/recvバイトストリームに追加/バイトストリームからデータを消費します。

Linuxでは、send/はソケット、ディスクファイル、パイプなどに使用される汎用的な/システムコールrecvの一種にすぎません。

異なるタイプのハンドルが同じ読み書きAPIを共有しているのは単なる偶然であり、TCPとUDPは意味的に互換性がないため、両方で動作するコードが存在する可能性は低いでしょう。readwrite



#### 概要

```
    TCPソケットを待機中:
    bind()＆listen()

    read()

    close()

```
